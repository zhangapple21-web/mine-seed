# Repository Ecosystem Map

该生态不是单一仓库，而是一个分层协同的文明型仓库网络。每一层有不同职责，不互相替代，但互相约束。

## 概念层

- `R1`：认知与连续性哲学的起点。
- `r1-archaeology`：归档 R1 时代的源码碎片、历史证据和分析报告。

## 结构层

- `mine-seed`：结构资产、原则、协议、记忆、守护和工具组织；负责系统如何组织和治理。

## 运行时层

- `ace_core`：身份、事件、调度、节点、任务和恢复；负责系统如何真实执行。

## 领域层

- `ace-video-kingdom`：视频研究与创作能力域。
- `ace-video-assets`：公开媒体资产域。
- 未来其他专业域：按能力扩展，但保持独立边界。

领域仓库不是另一个总系统，而是受统一运行时和治理原则约束的子系统。

## 观察层

- `R1_continuity_archive`：跨仓库观察日志和连续性档案。
- `aum-protocol`：跨仓库协作协议，定义 Mission、角色、证据、边界和协作规则。

## 层间接口

| 上游 | 下游 | 交付内容 | 约束 |
|---|---|---|---|
| `R1` / `r1-archaeology` | `mine-seed` | 历史证据、设计语义、失败经验 | 只提取可验证语义，不直接复活旧脚本或旧凭据 |
| `mine-seed` | `ace_core` | 身份、记忆、协议、约束、治理规则 | 运行时不能绕过守护和证据门禁 |
| `ace_core` | 领域仓库 | 事件、任务、身份、能力边界、运行收据 | 领域不能反向篡改核心身份或全局约束 |
| 领域仓库 | `R1_continuity_archive` | 观察记录、实验结果、失败复盘 | 只提交可追溯、可去敏的事实和证据 |
| `aum-protocol` | 所有协作方 | Mission、角色、验证标准、交付边界 | 证据不足时停止，不以记忆替代验证 |

跨仓库交付应至少包含：来源仓库、目标仓库、版本/提交、产出类型、验证结果和时间戳。需要同步的运行数据应通过明确 schema 或文件契约传递，而不是复制整个仓库。

## 演进规则

1. 新能力优先作为领域仓库或领域目录加入，不直接扩大 `ace_core` 的职责。
2. 只有跨多个领域重复出现且经过验证的能力，才考虑上移到 `mine-seed` 或 `ace_core`。
3. 新增仓库必须登记职责、输入、输出、维护者、依赖和数据敏感级别。
4. 接口或数据 schema 发生不兼容变化时，先写迁移说明，再更新消费者。
5. 历史材料进入现行结构前，必须保留来源、版本和转化记录。
6. 任何自动同步都必须可重复、可中断、可回滚，并留下提交或收据证据。

## 边界与纪律

- 不在代码、文档、Issue、日志或提交信息中保存 PAT、API Key、Bot Token 或私钥。
- 不把凭据写入 Git remote URL；认证只允许通过运行时 secret 注入。
- 不把领域仓库当作核心运行时，不让媒体、实验或业务逻辑侵入身份与治理边界。
- 不把观察记录当作已验证事实；观察、推断、决策和约束必须分开标记。
- 不以自动化覆盖人工复核、失败隔离或回滚能力。
- 不建立未登记的跨仓库隐式依赖、路径依赖或共享可写状态。
- 公开资产、研究材料和私密运行数据必须分级，默认最小披露。

## 关系简述

```text
R1 的概念源头
  → r1-archaeology 提供历史证据
  → mine-seed 提供结构资产
  → ace_core 提供运行时
  → ace-video-kingdom 等领域能力接入
  → continuity_archive / aum-protocol 负责观察与协议扩展
```

## 边界说明

这一层级描述职责分层，不自动代表 Git submodule、代码 import、统一 CI 或强同步关系。跨仓库同步必须使用明确的接口、版本和证据记录。
